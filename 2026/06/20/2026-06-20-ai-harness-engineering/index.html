一、什么是"工作环境保护框架"（Harness）



如果把 AI 编码智能体比作一个新入职的工程师，那么工作环境保护框架就是他的

"入职手册 + 任务清单 + 验收标准 + 交接文档"。它不是写业务逻辑的代码，而是

包裹在代码外面的一层规则和验证体系。


一个完整的 harness 包含五个子系统：


子系统 | 最小产物 | 解决的问题

  • --------------|----------------------|-------------------------------

    • 指令层 | AGENTS.md / CLAUDE.md | AI 进来第一步看什么？边界在哪？

    状态层 | feature_list.json | 哪些功能做了？哪些没做？

    验证层 | init.sh | 怎么知道代码没坏？

    范围层 | 功能依赖 + 完成定义 | 什么时候算做完？不能碰什么？

    生命周期层 | session-handoff.md | 换了一个新 AI，怎么快速接手？


这五个子系统贯穿下面全部 6 个项目，每个项目在某一两个子系统上深入。



二、项目全景图



Project 核心问题 新增 Harness 产物

  • ------- ---------------------------- ----------------------------------

    • P01 有 harness vs 没 harness？ CLAUDE.md, feature_list.json, init.sh

    P02 交接时丢不丢上下文？ session-handoff.md, 拆分文档

三、Project 01：基线对比——有 Harness 和没 Harness 差别有多大



3.1 实验设计


同一个 Electron 知识库应用，用两种方式让 AI 去实现：


  • starter（弱 harness）：只给一句模糊的话——

    • "构建一个可以显示文档并回答问题的 Electron 应用。"


  • solution（强 harness）：给完整的 AGENTS.md、feature_list.json、

    • init.sh、claude-progress.md。


3.2 四个功能


  • 窗口启动：Electron 窗口 1200x800，标题 "Knowledge Base"
  • 文档列表：左侧边栏显示导入的文档卡片
  • 问答面板：底部输入框 + IPC 通信
  • 数据目录：自动创建本地存储目录

3.3 核心结论


同一份代码，同一个 AI。差别只在于有没有 harness 文件。结果是：


  • 有 harness 的 AI 明确了"做到什么算完成"
  • 没 harness 的 AI 容易提前喊"好了"，实际功能残缺
  • feature_list.json 充当了"不可抵赖的验收单"


四、Project 02：跨会话上下文——换了个 AI 还能接着干吗？



4.1 实验设计


同一个功能拆成两个会话：


Session A：AI 写文档导入和详情视图，故意不写完就停止

Session B：新 AI 接手，只能从仓库里找线索继续


4.2 新增 Harness 产物


  • session-handoff.md：记录了"上次做到哪了、改了哪些文件、下一步做什么"
  • 拆分文档：ARCHITECTURE.md（架构）+ PRODUCT.md（需求），各管各的

4.3 核心结论


  • 没有交接文档 → 新 AI 花 10-20 分钟读代码猜进度
  • 有 session-handoff.md → 新 AI 花 30 秒定位，直接开始干活
  • 拆分文档比一个巨型文档有效：AI 按需加载，而不是每次都吃一本字典


五、Project 03：多会话连续性——反复重启，AI 会不会跑偏？



5.1 实验设计


在 P02 基础上新增 4 个功能（文档分块、元数据提取、索引状态 UI、带引用问答），

必须跨多个会话完成。中途故意停止，看 AI 能不能从 claude-progress.md 恢复。


5.2 新增 Harness 产物


  • claude-progress.md：跨会话的进度日志，每个功能做完写一笔
  • clean-state-checklist.md：启动前先检查环境干不干净
  • "一次一个功能"策略：AGENTS.md 里硬性规定只能一个一个做

5.3 功能依赖图（写在 AGENTS.md 里）


metadata-extraction → document-chunking → indexing-status-ui

↓

grounded-qa


5.4 核心结论


  • 没有进度日志 → AI 每次重启都"重头开始"，重复劳动
  • 有 claude-progress.md → AI 一眼看到做到哪了，继续往下推
  • "一次一个功能"策略避免了 AI 一次改 5 个文件结果全坏


六、Project 04：运行时反馈——代码坏了，AI 能自己找到 bug 吗？



6.1 实验设计


starter 的 IndexingService 里植入了一个 bug：大于 1000 字符的文件会产生空 chunk。

观察 AI 能不能通过日志定位并修复。


6.2 新增 Harness 产物


  • logger.ts：结构化 JSON 日志（带时间戳、服务名、日志级别）
  • check-architecture.sh：自动扫描渲染器有没有偷用 fs/path，服务层有没有偷引 electron

6.3 核心结论


  • 没有日志 → AI 只能读代码猜 bug，猜半天
  • 有结构化日志 → AI 看到空 chunk 的日志，直接定位到对应代码
  • check-architecture.sh 秒级发现越界调用，不用人工 code review


七、Project 05：角色分离——多个人检查比一个人检查强多少？



7.1 实验设计


同一个功能（ConversationHistory 对话历史组件），用三种 AI 角色配置各实现一遍：


变体 A（single-role）：一个 AI 自己规划、自己写、自己审查

变体 B（gen-eval）：一个 AI 写 + 另一个 AI 审查打分

变体 C（plan-gen-eval）：一个 AI 规划 + 一个 AI 写 + 一个 AI 审查


7.2 新增 Harness 产物


  • sprint-contract.md：规划师写的，10 条验收标准 + 范围边界 + 不在范围内的部分
  • evaluator-rubric.md：审查员用的评分表（功能完整性、视觉设计、交互性、代码质量等 8 个维度）

7.3 结果对比（同一个功能，同一个模型）


| 特性 | Single-Role | Gen-Eval | Plan-Gen-Eval |

|------------|-------------|-------------|----------------|

| 聊天气泡 | ❌ 没有 | ✅ 有 | ✅ 有 |

| 时间戳 | 长格式 | 紧凑格式 | 紧凑 + 日期分隔 |

| 引用展示 | ❌ 完全没有 | 只显示数量 | ✅ 可展开完整引用 |

| 一键复制 | ❌ 没有 | ❌ 没有 | ✅ 有 |

| 追问建议 | ❌ 没有 | ❌ 没有 | ✅ 有 |

| 评分 | 1.6 / 5 | 3.3 / 5 | 4.9 / 5 |


Plan-Gen-Eval 经历了 3 轮修订：4.2 → 4.6 → 4.8 → 4.9


7.4 核心结论


  • 不是 AI 能力不行，是一个人干所有事不行
  • 加一个独立的审查员，质量直接翻倍
  • 再加一个规划师提前定好验收标准，质量再翻一倍
  • 三轮修订从 4.2 提到 4.9 的过程，就是"评估器循环"的核心


八、Project 06：顶点项目——给你的代码装上仪表盘



8.1 实验设计


starter 和 solution 的产品代码几乎一样。差距全在"运维层"：


  • starter：只有一个 AGENTS.md
  • solution：全套 harness + 三个运维脚本

8.2 新增 Harness 产物


  • benchmark.sh：性能基准测试，测导入速度、索引吞吐量、查询延迟
  • cleanup-scanner.sh：数据完整性扫描，

    • 检查：孤儿内容文件？悬空 chunk？元数据不一致？过期 Q&A 引用？

  • check-architecture.sh：架构边界检查，

    • 检查：渲染器有没有偷用 fs？服务层有没有偷引 electron？React 有没有泄漏到主进程？

  • quality-document.md：质量评分追踪
  • docs/RELIABILITY.md：可靠性文档

8.3 核心结论


  • 同一份产品代码，弱 harness 下你不知道它健不健康
  • 强 harness 下，三行命令（benchmark、cleanup-scanner、check-architecture）

    • 就能量化一切：性能、数据完整性、架构合规性

  • 这就是"可观察性属于工作环境保护框架"的含义


九、Skills：harness-creator——把学到的变成能复用的



课程不只是 6 个项目，还包含了一个可复用的 skill：


skills/harness-creator/

├── SKILL.md ← AI 读了就知道怎么生成 harness

├── templates/ ← 空白模板（AGENTS.md、feature-list.json、init.sh 等）

├── scripts/ ← 自动化脚本（生成、验证、基准测试）

└── references/ ← 7 个高级模式文档


9.1 它能干什么


给 AI 加载这个 skill，然后说"为这个项目生成一套 harness"，AI 会：

1. 读项目文件，理解项目类型

2. 选模板，填占位符

3. 生成 CLAUDE.md、feature_list.json、init.sh、session-handoff.md 等


9.2 7 个参考模式


  • 内存持久化模式
  • 上下文工程模式
  • 技能运行时模式
  • 工具注册表模式
  • 多智能体协调模式
  • 生命周期与引导模式
  • 陷阱与误区

9.3 与 6 个项目的关系


6 个项目教的是"为什么要这么做"和"手写怎么做"，

harness-creator 是"自动化生产线"——下次不用手写，一键生成。

十一、如果你只记住 5 件事



1. feature_list.json 是 AI 的"不可抵赖的验收单"——pass 就是 pass，

fail 就是 fail，没有灰色地带。


2. session-handoff.md 是最便宜的保险——花 5 分钟写，省下次 20 分钟猜。


3. 拆分文档，不要巨型文件——AGENTS.md 管行为规则，ARCHITECTURE.md

管架构，PRODUCT.md 管需求。AI 按需加载，效率高 10 倍。


4. 一个 AI 干所有事不如分工——规划师定标准 + 写手写代码 + 审查员打分，

同一功能质量从 1.6 分拉到 4.9 分。


5. 运维脚本是 harness 的一部分——benchmark.sh、cleanup-scanner.sh、

check-architecture.sh 让你的项目从"能跑"变成"可度量"。

十三、如何复现这些实验



1. 每个项目都有 starter/ 和 solution/ 两个目录

2. starter 是弱 harness 版本 —— 从这里开始实验

3. solution 是强 harness 版本 —— 这是参考实现

4. 流程：

cd starter && npm install

让 AI 根据 starter 里的 prompt 完成任务

观察完成率和行为

对比 solution 的结果

5. 启动命令（所有项目通用）：

npm run dev # 构建并启动 Electron 应用

npm run check # TypeScript 类型检查

npm run build # 仅构建

npm test # 运行测试
